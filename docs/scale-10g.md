# 撑到 10GB：现状、瓶颈与分阶段改造

这份文档回答一个问题：**当前这个内核，离「10GB 数据 + 快速读写查询」还差什么，差多少。**

所有数字都是本机实测（Intel i7-1068NG7 / Node 22.22 / macOS），脚本在 `bench/` 下可复现。
没有实测支撑的判断会明确标注「估算」。

---

## 1. 先把 10GB 换算成行数

| 规模 | 行数 | 文件 | 实测来源 |
|---|---|---|---|
| 10 万行 | 100,000 | 17.6MB | `bench/scale.ts --rows 100000` |
| 30 万行 | 300,000 | 53.8MB | 同上 |
| 100 万行 | 1,000,000 | 153.5MB | 同上 |
| **10GB** | **约 6,600 万行** | 10GB | 按 161 字节/行外推 |

每行 161 字节是本仓库压测数据的形态（5 个字段，其中 2 个枚举 2 个数值 1 个中文名）。
真实业务对象更大，行数会相应更少；**下面的结论按行数说话，不按字节**。

---

## 2. 实测：当前架构随规模怎么变

| 行数 | 快照 open | 逐页重放 | 索引常驻堆 | 每行索引成本 |
|---|---|---|---|---|
| 100,000 | 114ms | 477ms | 10.2MB | 102 B |
| 300,000 | 456ms | 1,538ms | 38.0MB | 127 B |
| 1,000,000 | 1,395ms | 5,159ms | 89.3MB | 89 B |

三条曲线都是**近似线性**，这既是好消息也是坏消息：

- 好消息：没有隐藏的平方项，算法复杂度是对的，不需要推倒重来。
- 坏消息：线性意味着 **10 倍数据就是 10 倍代价**，而 66 倍数据会直接撞墙。

外推到 6,600 万行：

| 指标 | 外推值 | 说明 |
|---|---|---|
| 索引常驻内存 | **约 6.0GB** | 89 B/行 × 6669 万 |
| 冷启动（快照） | **约 90 秒** | 1.4µs/行 × 6669 万，且这是乐观值 |
| 冷启动（重放） | 约 5.7 分钟 | 不可接受，只作为兜底 |
| 全量导入 | **约 44 分钟** | 2.5 万行/秒 |

**结论：当前架构在 10GB 下不可用。** 不是慢一点，是「打开要一分半、吃 6GB 内存」。

---

## 3. 三个硬门槛，按必须先解决的顺序

### 门槛 1：key→位置 的映射全在内存（6.0GB）

内存里其实有**四份**按 key 索引的结构，不是两份：

| 结构 | 位置 | 用途 |
|---|---|---|
| `index: Map<string, number>` | `src/pagetable.ts` | key → 逻辑页号 |
| `rowids: Map<string, number>` | `src/bizindex.ts` | key → rowid |
| `keys: string[]` | `src/bizindex.ts` | rowid → key（反向） |
| `idx: Map<string, Map<string, Entry>>` + `order` | `src/store.ts` | shell 命名空间的 KV 索引 |

最后一份只在 shell 里有数据时才建（`bizPut` 不写 shell 行，所以纯业务表模式走得掉），
但走重放路径时它对每个 shell key 都会建一个 `Entry` 对象，是最贵的一份。

6600 万个 key × 4 份结构 = 6GB。这是最先崩的一块，也是阶段 2 要整体替换的对象。

> 想只优化其中一份是不划算的：按实测，把 `Rowids` 换成「开放寻址 + 字节 arena」
> 的紧凑索引，单份能从 53 B/行 降到 29 B/行，但四份摊下来总量只降 1.3×，
> 离阶段 2 要求的 15MB **差一个数量级**。要么整体换成落盘索引，要么不动。


### 门槛 2：冷启动要把 6GB 索引一次性建好

快照虽然把「重放」换成了「一次 pread + 解码」，但解出来的东西仍要全部驻留内存。
数据量超过物理内存时，快照文件本身就成了 swap 的受害者，加速比会崩掉。

### 门槛 3：写入是单写者，且写放大 1.6×

CoW 页表每改一行重写整页（4KB），实测写放大 1.6×。
10GB 导入 44 分钟，其中约 26 分钟是在重写没变的字节。

## 4. 分阶段改造

每个阶段都有**可验证的验收判据**，做完才能进下一个。
判据全部能用 `bench/` 下的脚本量出来，不靠感觉。

### 阶段 1 · 谓词剪枝（已完成）

**做了什么**：数值列按 4096 行分块，每块记 min/max。区间查询先问块统计，
整块不可能命中就跳过；命中率太高（剪不掉 1/4 以上）时自动退回全量遍历，避免「剪枝本身成为开销」。

| 场景（100 万行） | 全表扫 | 块剪枝 | 加速 |
|---|---|---|---|
| 命中 0.01% | 6.44ms | 0.06ms | **~105×** |
| 命中 0（区间落在空隙） | 6.22ms | 0.02ms | **~230×** |
| 命中 20%（取前 50） | 2.47ms | 0.05ms | **~47×** |
| 命中 20%（取全部 20 万行） | 17.03ms | 11.50ms | 1.5× |
| 命中 100% | 61.87ms | 60.20ms | 1.0×（无退化） |

统计开销：4096 行一块 × 16 字节 = **4KB / 100 万行**，10GB 下也只有 260KB。

**验收**：`npm run bench:predicate -- --rows 1000000`，五档全部 ≥1.0×，且逐行结果与全表扫一致。

> 这套数字重测过两轮，原因都是**基准本身在骗人**，不是内核变了：
>
> 1. 原先用 `salary` 字段测区间查询，但它不在 `DEFAULT_NUM_FIELDS`
>    （`level/updated_at/ms/bytes`）里，查询走的是「字段不存在 → 立刻返回空」的快路径。
>    那个 21.9ms 是「为返回空而扫完全表」，不是区间扫描。现在基准用 `ms`，是真区间。
> 2. 原先「旧算法连跑 40 次、再新算法连跑 40 次」，命中 100% 那档报成 **0.9×**，
>    看起来新算法更慢。真实原因是后跑的算法要承受前面积累的 GC 压力——改成交错测量后
>    同一份数据是 **1.0–1.1×**。**任何固定顺序的 A/B 都在给后跑的那个扣分。**
> 3. 「候选块 / 总块」的分母曾经用 `capacity`。它是按 2 的幂翻倍的，尾上一串空块
>    从没写过、本来就不算候选，却把比例稀释掉，于是「所有有数据的块都命中」
>    这种最该退回全量的情形被判成「剪得挺好」。分母改成 `ceil(nextRowid / 4096)`。

### 阶段 2 · key 索引落盘（已实现，待百万 / 千万行验收）

**目标**：把 6.0GB 的 Map 换成「磁盘有序块 + 内存稀疏索引」。

结构（照 SSTable 做，不发明新东西）：

```
磁盘：有序 key 块（每块 4KB，块内按 key 排序，存 [keyLen][key][logicalPage]...）
内存：每块首 key + 块偏移 + Bloom filter
查找：二分稀疏索引 → 定位一块 → 一次 pread → 块内二分
```

内存账（6600 万行，按每块 ~90 个 key 估）：

| 部件 | 体积 |
|---|---|
| 稀疏索引（73 万条 × 16B） | 12MB |
| 块级 Bloom（73 万 × 10 bit） | 0.9MB |
| 页缓存（热块 LRU，可配） | 默认 64MB |
| **合计** | **约 77MB**（对比现在的 6.0GB） |

**验收判据**：

1. 100 万行时 `open 快照` 的 heap 增量 **从 89.3MB 降到 15MB 以下**
2. 点查热缓存 p50 **≤ 10µs**（现在 82ns，允许退化一个量级，因为换来的是 400 倍内存）
3. 点查冷缓存 p50 **≤ 100µs**（一次 pread）
4. 1000 万行时 open **≤ 300ms**
5. 全部现有用例通过，包括 `bruteForce` 对拍

**这一阶段会改磁盘格式**（新增 key 块），需要 `format_ver` 升级 + 迁移路径。

### 阶段 3 · 数值列与位图分块落盘

数值列现在是一整条 `Float64Array`（6600 万 × 8B = 530MB/列）。
改成按块存盘，块统计数据留在内存：

| 粒度 | 块数（6600 万行） | 统计体积 | 命中 20% 要读 |
|---|---|---|---|
| 4096 行 | 16,300 | 260KB | 106MB（太慢，约 88ms） |
| 65536 行 | 1,007 | 16KB | 10MB（约 8ms） |

所以要**两级**：64K 行一个大块（决定读多少），大块内再按 4096 行记子块统计（决定剪多准）。

位图同理：每 64K 行一段，只把命中的段读进内存，段级缓存淘汰。
在这之前需要先确认位图是不是真的瓶颈——按 8 个位图算，6600 万行也只有 66MB，
**不是瓶颈**；只有当枚举字段数上百时才需要动。

**验收判据**：10GB 数据下 `{gte, lte}` 区间查询 **≤ 50ms**（命中 20%），≤ 5ms（命中 0.1%）。

### 阶段 4 · 写入吞吐

现在 2.5 万行/秒，10GB 导入 44 分钟，其中约 60% 是重复写没变的字节。

两条路，可以叠加：

1. **compaction**：同页多次 CoW 后只留最后一版，回收中间版本。解决写放大。
2. **按 key 分区多写者**：把 key 空间哈希到 N 个独立段，每段一个单写者，
   N 个线程并行。内核现在「单写者」的前提不用破，只是变成「每分区单写者」。

**验收判据**：导入 1000 万行 **≤ 4 分钟**（即 ≥ 4.2 万行/秒），写放大 **≤ 1.2×**。

## 5. 不做的事（明确划出去，免得反复讨论）

| 不做 | 理由 |
|---|---|
| 完整 SQL | 筛选器语义（eq / gte / lte）+ 分页已经覆盖本项目的全部访问模式 |
| 事务隔离级别 | 单写者 + 崩溃安全（CoW + CRC）已经够用；加 MVCC 会把 6GB 变成 18GB |
| 网络复制 / 集群 | 这是「本地 App 的嵌入式存储」，不是数据库服务 |
| 向量索引 | 等真有人要用再说。列存旁路在 `docs/design.md` 里有设计，没实现 |

## 6. 怎么自己复现

```bash
# 规模曲线：每行索引成本、open 随行数变化、外推 10GB
node --expose-gc bench/scale.ts --rows 1000000

# 区间查询 A/B：全表扫 vs 块剪枝，逐行比对结果
node --expose-gc bench/predicate.ts --rows 1000000

# 冷启动：快照 vs 重放，同库两条路 + 结果一致性
node bench/open.ts --rows 30000 --rounds 3
```

三条命令都自带「结果一致」断言。**性能数字只有在结果一致的前提下才有意义**——
快照或剪枝一旦和全表扫不一致，那是数据正确性问题，不是性能问题。

### 三条测量纪律（都踩过）

1. **必须 `--expose-gc`**。不强制 GC 就量到一堆垃圾，数字随上一步操作漂。
2. **对照组要做等量的事**。曾把「只返回 rowids」的旧算法和「返回 rowids + keys」的
   新算法对比，于是新算法在高命中率下显得慢一倍——其实是多建了一个 6 万字符串的数组。
3. **内存口调用哪个，决定你能不能看见 TypedArray**。`heapUsed` **不含** `Float64Array`
   这类 TypedArray 的底层 buffer；`external` 才含，而 `arrayBuffers` 是 `external` 的子集
   （两个都加就是重复计数）。曾用 `heapUsed` 做因子分解，得出「给索引加 4 个数值列、
   100 万行 32MB，内存一点没涨」的荒谬结论——不是没涨，是那个口径看不见。
   要么统一用 `heapUsed + external`，要么按字段配置各跑一遍对比 `rss`。
